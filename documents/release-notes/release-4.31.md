# Release 4.31

**Form (Dynamic Flow)** can now take the flow to run from a link, and guests finally see the **Calendar/Scheduler** in their own language.

- **Choose the flow from the URL** (#618): a placed **Form (Dynamic Flow)** component runs the flow named in the page's own address when one is supplied, instead of the flow fixed in its configuration. One component on one page can now serve many flows from different links, which is how the retired Aura flow-display component worked and the main reason people were still using it. Accepted as `flowApiName` or `flowName`, in either the plain or the `c__` prefixed spelling, and the case does not matter. Use the `c__` form on Lightning app pages: **Lightning Experience silently discards query parameters that are not `c__` namespaced**, so a plain spelling never arrives. Experience Cloud, Visualforce and the embed page pass either through.
- **The configured flow is still required and still the fallback.** Nothing changes for existing components: with no parameter in the URL, the flow you picked runs exactly as before. A parameter naming a flow that does not exist, or one that is not an active screen flow, shows the standard flow error rather than failing silently.
- **Guests see translated dates in the Calendar/Scheduler** (#619): on an Experience Cloud site, a guest choosing a date saw English month names, English weekday headers and an English selected-date line, even with the site's language selector set to something else and even though every custom label on the same screen translated correctly. Month names, weekday headers, the selected-date line and the date and time on each record now follow the visitor's **language**, so a Spanish visitor gets Spanish names and Spanish conventions throughout.
- **Why it looked like a Schedule-versus-record-mode problem.** It was reported as translation working in one mode and not the other, but the two modes were being viewed in different contexts: logged in versus guest. A logged-in user was always localized correctly. The cause was that dates were formatted from the **guest user record's Locale**, which defaults to English and never follows the visitor's browser or the site's language selector, while custom labels travel on the visitor's language. The two now agree.
- **The same fix reaches the stage indicator's "last saved" text**, which had the identical problem on the same pages. Logged-in users see no change anywhere, because language and locale already agreed for them.

Admins: load your public form pages, including any embedded form URLs, once after upgrading; the first visit pays the component compile so a real visitor does not.
